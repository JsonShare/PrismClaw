# PrismClaw 业务域功能架构规范

> 本规范定义业务域的目标形态。业务域是系统内的**功能模块与功能页面集合**，不是专家、专家团队、技能包或插件体系的另一种实现。
>
> `DomainBundle` 仅是业务模块的内部装配接口，不代表业务域具有独立 Agent 能力。医疗、法律等域的详细设计必须遵守本规范；旧文档中有关域技能、域插件、域 Agent、独立模型流水线的描述，按第十四节迁移，不再作为新增功能的依据。

## 一、定位

业务域负责把某一类业务做成可使用、可管理、可持续操作的功能页面，并调用系统核心能力完成其中的智能任务。

一句话概括：**入口和业务能力在域，智能执行在核心，专业知识与流程复用现有专家，结果回到业务页面。**

业务域的价值包括：

1. 为明确业务场景提供表单、列表、详情、看板、操作按钮和结果视图。
2. 管理业务对象、业务规则、业务流程和业务数据。
3. 把页面输入整理成标准任务，提交给系统核心 Agent 或现有专家。
4. 展示核心任务的进度、结果和产出物，并按业务规则保存结果。

业务域不承担以下定位：

- 不是第二个系统 Agent。
- 不是某个专家或专家团队的页面化复刻。
- 不是独立技能市场、插件容器或 MCP 集合。
- 不是独立于系统会话、任务、文件和权限体系的另一套运行时。

## 二、核心原则

| 原则 | 规范 |
|---|---|
| **功能页面优先** | 业务域首先交付可操作的页面和业务闭环，而不是人格、提示词、专家头像或团队编排。 |
| **核心统一执行** | 所有需要模型推理的任务均由系统核心 Agent 运行时执行，业务域不得自建 Agent Loop 或独立 LLM 执行链。 |
| **专家直接复用** | 需要专业能力时，直接选择系统已注册的现有专家；专家团队也作为核心已有执行单元复用。 |
| **不建平行能力体系** | 业务域不新增独立 Agent、专家、技能、插件、命令、MCP、工具目录或模型配置体系。 |
| **确定性与智能分离** | 增删改查、计算、校验、状态流转由业务服务完成；分析、审查、生成、总结、咨询等智能任务交给核心。 |
| **核心状态唯一** | 会话、运行、事件、任务进度、取消、恢复和产出物状态由核心维护，业务域只保存业务状态及核心 ID 关联。 |
| **权限不扩大** | 从业务页面发起的任务继承当前用户、工作区、会话和核心安全策略，不因入口不同而绕过治理。 |

## 三、职责边界

### 3.1 业务域负责

| 层次 | 可以承载的内容 |
|---|---|
| 页面 | 菜单、表单、列表、详情、筛选、上传、操作按钮、结果展示、异常提示。 |
| 业务接口 | 业务对象的 CRUD、查询、导入导出、业务动作、业务记录与核心会话的关联。 |
| 业务服务 | 参数校验、权限内数据读取、确定性计算、状态流转、任务输入组装、结果校验与落库。 |
| 业务数据 | 业务表、业务索引、业务文件元数据，以及 `session_id`、`conversation_id`、`task_id` 等关联字段。 |
| 页面交互 | 发起核心任务、复用核心会话组件、订阅核心事件、跳转到核心会话或产出物。 |

### 3.2 系统核心负责

- 核心 Agent、Agent Loop 和模型调用。
- 专家与专家团队的注册、选择、执行和生命周期。
- 技能、工具、连接器、MCP 及其调用治理。
- 会话、对话历史、上下文、记忆、压缩和恢复。
- 任务调度、运行状态、事件流、取消和重试。
- 文件、工作区、沙箱、权限、安全和审计。
- 模型 Provider、模型路由、凭据和默认模型。
- 通用产出物及其存储、预览和下载。

### 3.3 业务域禁止新增

以下内容不得以“业务域需要”为由重新建设：

1. `agents/`、`experts/`、`.plugin/`、`plugins/`、`skills/` 或域级 `SKILL.md`。
2. 域专属专家人格、专家团队、团队角色分工或子 Agent 编排。
3. 域专属 Agent Loop、模型客户端封装、Provider 配置或独立多 Agent 流水线。
4. 与核心并行的技能目录、工具目录、插件目录、命令系统或 MCP 配置。
5. 与核心并行的聊天协议、会话存储、事件流或任务状态机。
6. 通过一段提示词在域内隐式重建“第二个专家”。任务模板只能描述本次任务目标、输入、输出和业务约束，不能定义长期人格、团队身份或独立运行规则。

> 业务确定性代码不是插件。页面组件、业务 API、业务服务、数据模型和持久化实现均属于允许建设的功能代码。

## 四、业务域、核心 Agent 与专家的关系

```text
用户
  │
  ▼
业务域功能页面
  ├─ 确定性操作 ───────────────► 业务 API → 业务服务 / 业务数据
  │
  └─ 智能任务 ─────────────────► 核心公开会话 / 任务入口
                                   │
                                   ├─ 默认：系统核心 Agent
                                   │
                                   └─ 按需：现有专家 / 现有专家团队
                                                │
                                                ├─ 复用核心技能与工具
                                                ├─ 复用核心连接器与 MCP
                                                └─ 遵守核心会话、权限与治理
                                   │
                                   ▼
                         核心事件 / 结果 / 产出物
                                   │
                                   ▼
                         业务页面展示或校验后保存
```

关键约束：

- 业务域**可以发起和跟踪核心任务**，但不能接管核心任务的执行权。
- 核心 Agent 是默认执行者；现有专家是可选执行者，不是每个业务域的固定配套物。
- 业务域不直接调用某个技能、插件或 MCP 来完成旁路执行，统一由核心 Agent 或专家按核心规则调度。
- 业务域不复制专家的展示主页、人格设定和团队管理，只在具体功能中声明“本任务使用哪个现有执行者”。

## 五、功能分类与执行链路

### 5.1 纯业务功能

适用：列表查询、档案创建、状态修改、人工指派、归档、筛选、固定格式导出、确定性计算等。

```text
页面 → 业务 API → 参数与权限校验 → 业务服务 / Store → 返回页面
```

此类功能不得为了“统一 AI 化”而强行经过 Agent。

### 5.2 页面动作型智能任务

适用：合同审查、合规检查、病历摘要、报告分析、文书生成、风险提取等。

```text
页面提交业务参数
  → 业务 API 校验并读取必要上下文
  → 调用核心公开会话 / 任务应用服务
  → 核心 Agent 或指定现有专家执行
  → 核心返回事件、结果或产出物引用
  → 业务域校验结构化结果并按需保存
  → 页面展示结果
```

业务页面可以显示“分析中”“待确认”“已完成”“失败”等状态，但状态事实来自核心事件，不在前端自行推测。

### 5.3 页面内连续咨询

适用：患者详情咨询、案件上下文问答、审查结果追问等。

- 复用核心会话创建、消息发送、事件订阅和历史查询能力。
- 业务域只登记业务对象与核心 `session_id` 的关系，并提供必要的业务上下文。
- 页面可嵌入核心对话组件或复用核心交互协议，但不另建 `/agent/chat` 之类的平行聊天后端。
- 连续追问必须沿用同一核心会话，确保专家选择、上下文、权限和历史一致。

## 六、核心能力调用规范

### 6.1 调用方式

业务域可以使用两类核心公开入口：

| 场景 | 调用方式 |
|---|---|
| 后端业务动作需要执行智能任务 | 调用核心公开的会话 / 任务应用服务，由其构造标准核心运行请求。不得直接实例化 Engine、Agent Loop 或模型客户端。 |
| 前端需要连续对话或实时事件 | 使用核心既有 HTTP / WS 会话接口和事件协议，不在域内复制一套协议。 |

核心应用服务是业务域与执行引擎之间的边界。业务域不得依赖 Engine 内部私有类、私有目录或内部状态来完成任务派发。

### 6.2 逻辑任务参数

下表描述业务域提交核心任务时必须表达的信息，**不是新增一套 HTTP 协议**；落地时映射到核心既有会话、消息或任务接口。

| 参数 | 必填 | 含义 |
|---|---|---|
| `domain` / `function` | 是 | 标识来源业务域与功能，用于审计、上下文和结果回写。 |
| `executor` | 是 | `core` 表示核心 Agent；`expert` 表示使用现有专家，并携带 `expert_id`。 |
| `user_id` / `workspace_id` | 是 | 继承当前用户与工作区，由服务端可信上下文提供，不能由页面任意伪造。 |
| `session_id` / `conversation_id` | 按场景 | 连续任务沿用已有会话；新任务由核心创建。 |
| `input` | 是 | 当前任务文本、结构化参数、附件和业务对象引用。 |
| `business_context` | 按需 | 完成任务所需的最小业务快照或可读资源引用，不拼接整库数据。 |
| `output_contract` | 按需 | 页面消费所需的结构、字段或产出物类型。 |
| `client_request_id` | 建议 | 防止重复点击造成重复业务动作或重复结果落库。 |

### 6.3 执行者选择

1. 默认使用系统核心 Agent。
2. 只有功能确需专业流程、专业知识或专门工具治理时，才选择现有专家。
3. 指定专家时使用核心注册表中的稳定 `expert_id`，业务域不保存专家人格正文或复制专家配置。
4. 现有专家团队通过其核心专家身份调用，业务域不得拆解并重新编排团队成员。
5. 专家不存在、未启用或无权使用时，页面必须明确展示核心返回的错误；不得静默换成另一个专家，也不得由业务域临时模拟该专家。
6. 是否允许用户切换执行者由具体功能规范决定；未提供切换时，默认策略必须清晰、稳定、可审计。

### 6.4 结果回写

- 模型输出进入业务表前，业务域必须按业务 Schema 校验，不信任模型直接写库。
- 核心业务数据写入仍由业务 API / Store 完成，模型和专家不持有数据库凭据。
- 文档、表格等通用产出物优先使用核心产出物能力，业务记录保存其引用。
- 业务域可以保存“已采纳 / 已驳回 / 已归档”等业务状态，但不能复制核心运行状态作为第二事实源。

## 七、业务上下文与数据边界

1. 页面和业务 API 负责确认当前用户有权读取业务对象。
2. 发给核心的上下文应最小化，只包含当前功能所需字段、文件和资源引用。
3. 大文件优先传核心文件引用或产出物引用，不把完整二进制或大段无关文本塞入任务参数。
4. 业务域可以登记 `domain + record_id + session_id` 的关联，核心会话仍是消息与执行历史的唯一事实源。
5. 跨域数据访问必须经由目标业务域公开业务接口或核心公开能力，不得直接读写其他域的数据表。
6. 脱敏、权限、审计和安全要求在业务 API 与核心治理链分别落实；任何一侧都不能替代另一侧的边界校验。

## 八、前端功能页面规范

### 8.1 导航与装载

- `scripts/compile/domains.yaml` 是业务域菜单、前端分包和构建裁剪的注册表，不是专家、技能或插件注册表。
- 后端 `DomainManifest` 由注册表编译产物生成，前端通过域注册表懒加载 `WorkbenchPage`。
- 核心 `DomainSection` 负责承载业务页面，业务域不替换核心侧栏、会话容器或全局任务中心。
- 页面深链统一使用当前系统路由约定：`?domain={domain}&page={page}`，页内次级状态可增加域内参数。

### 8.2 页面组成

业务页面应围绕业务对象和任务闭环组织，至少明确：

- 输入区：业务对象、参数、附件和操作条件。
- 操作区：确定性操作与智能任务操作清晰区分。
- 状态区：复用核心任务进度、等待确认、失败和取消状态。
- 结果区：结构化结果、证据来源、产出物和后续业务动作。
- 历史区：按需关联核心业务记录或核心会话，不复制完整聊天历史数据库。

### 8.3 不应出现的页面定位

- “某域专属 AI 专家”主页或专家团介绍页。
- 与系统专家管理重复的人格、技能、插件配置页。
- 与系统聊天页完全平行、仅换名称和提示词的独立聊天应用。
- 让业务用户配置 Agent Loop、模型 Provider、团队成员或底层工具白名单的页面。

### 8.4 共享设计

业务页面沿用系统主题变量、按钮、输入框、卡片、加载态和错误态。业务域可以定义自身业务布局，但不建立第二套全局主题系统。

## 九、后端模块与装配规范

> 目录级落地方案与代码骨架见 [业务域分包标准范本](./domain-package-template.md)。

### 9.1 推荐结构

```text
backend/src/subpackages/<domain>/
├── integration/       # 仅负责模块装配与核心公开端口接线
├── api/               # 业务 HTTP 接口
├── services/          # 确定性业务逻辑、核心任务输入组装、结果校验
├── models/            # 业务请求、响应与视图模型
├── domain/            # 业务规则与领域模型
├── persistence/       # 业务 Store
└── deploy/sql/        # 业务表 DDL 自建脚本，启动时自动扫描

frontend/subpackages/<domain>/
├── <Domain>WorkbenchPage.tsx
└── src/
    ├── pages/
    ├── components/
    ├── api/           # 业务 API 与核心公开 API 的客户端调用
    └── styles/
```

目录中不出现独立的 `agents`、`experts`、`skills`、`.plugin`、`plugins` 或域级 MCP 配置。

### 9.2 DomainBundle 的定位

`DomainBundle` 是核心装配业务模块的 Protocol，只承担：

- 提供页面和菜单 Manifest。
- 注册业务数据存储。
- 注册业务 API 路由。
- 装配业务服务与核心公开会话 / 任务端口。
- 启动确实属于业务功能的后台工作，并接入核心生命周期。

它不再承担以下职责：

- 注册域专家、域技能或域插件。
- 向核心注入一套域专属 Agent 工具面。
- 创建域专属 Agent 会话运行时。
- 改变核心 Agent、专家和技能的归属关系。

既有 `DomainRuntimeContext` 中面向域工具、域技能、域钩子和域治理扩展的注册方式属于存量迁移范围，不是新业务域的标准接入方式。业务权限与输入校验优先落在业务 API；通用智能任务治理由核心统一执行。

### 9.3 路由边界

- 业务域拥有 `/api/<domain>/...` 下的业务资源与业务动作接口。
- 核心拥有会话、消息、任务、事件、专家和产出物接口。
- 业务域可以保存核心会话关联，但不新增与核心等价的 `/api/<domain>/agent`、`/skills`、`/experts` 或 `/plugins` 体系。

### 9.4 SQL 自建脚本

业务域的建表 DDL 是域自有资产，随域包存放；仓库根 `deploy/sql/` 只保留核心 `init_postgres.sql`。

| 项目 | 规范 |
|---|---|
| 位置 | `backend/src/subpackages/<domain>/deploy/sql/` |
| 命名 | `<3 位序号>_<描述>.sql`（如 `001_init.sql`），按文件名升序执行 |
| 触发 | 系统启动装配域后自动扫描，Bundle 不写任何 schema 调用 |
| 幂等 | 语句使用 `IF NOT EXISTS`；每个文件独立持有 advisory lock |
| 失败 | 记入 `/api/domains/status`，不阻断服务启动 |
| 无表 | 没有 `deploy/sql` 目录视为无业务表，正常跳过且不报错 |

扫描与执行由核心 `apply_domain_sql` 统一实现；域包不得自带 SQL 执行器、迁移框架或版本表。

## 十、状态与异常规范

| 状态 | 唯一责任方 | 业务域可做的工作 |
|---|---|---|
| 业务对象状态 | 业务域 | 创建、修改、归档、采纳结果、保存业务版本。 |
| 会话与消息状态 | 核心 | 保存关联 ID，读取或跳转，不复制消息事实。 |
| 智能任务运行状态 | 核心 | 展示核心事件，保存 `task_id` / `session_id` 关联。 |
| 产出物状态 | 核心 | 保存业务对象与产出物引用，提供页面入口。 |
| 业务校验结果 | 业务域 | 拒绝不合法输入或不合格模型结果，并给出可操作提示。 |

异常处理要求：

- 业务校验失败由业务 API 返回明确错误，不启动核心任务。
- 核心任务失败、取消或等待确认时，页面如实呈现核心状态，不伪造业务成功。
- 核心成功但业务结果校验失败时，保留核心结果引用，将业务记录标记为待处理或校验失败，不写入不完整业务数据。
- 重复提交按业务幂等键处理，避免同一业务动作重复落库。

## 十一、权限、安全与审计

1. 所有页面任务都在当前用户身份下执行，服务端从认证上下文获取用户，不信任客户端自报身份。
2. 业务域先校验业务对象访问权，核心再按会话、工作区、专家和工具策略执行，两层均不得绕过。
3. 指定专家只改变核心执行者，不扩大业务数据访问范围。
4. 业务审计至少记录来源域、功能、业务对象、核心执行者、核心会话或任务 ID、结果处理状态。
5. 敏感数据的读取、传输、展示和落库遵循对应业务域的合规要求；模型输出不能作为解除脱敏或越权展示的依据。

## 十二、单功能规范模板

每个业务功能页面必须写清以下内容，缺项不得进入实现：

| 项目 | 必须回答的问题 |
|---|---|
| 功能目标 | 用户完成什么业务闭环？页面交付什么结果？ |
| 业务对象 | 操作哪些业务实体？数据归谁所有？ |
| 页面交互 | 输入、按钮、列表、详情、进度、结果和历史如何组织？ |
| 确定性流程 | 哪些步骤由业务服务直接完成？ |
| 智能任务 | 哪些步骤需要核心 Agent？输入和输出契约是什么？ |
| 执行者 | 默认核心 Agent，还是某个已注册专家？是否允许用户切换？ |
| 上下文 | 需要哪些最小业务字段、文件和资源引用？ |
| 结果处理 | 如何校验、展示、采纳、保存或跳转入核心产出物？ |
| 状态与异常 | 如何处理运行中、等待确认、失败、取消、重复提交和校验失败？ |
| 权限与审计 | 谁可访问、记录哪些关联 ID、是否涉及敏感数据？ |
| 验收标准 | 如何证明页面闭环完成，且没有新增平行 Agent / 专家 / 技能体系？ |

## 十三、新增业务域检查清单

新增或重构业务域时，必须同时满足：

- [ ] 交付物以功能页面和业务闭环为中心。
- [ ] 默认智能任务可以由系统核心 Agent 执行。
- [ ] 专业任务只引用现有专家或现有专家团队。
- [ ] 没有域级 Agent、专家、技能、插件、命令或 MCP 目录。
- [ ] 没有独立模型调用、Agent Loop 或多 Agent 流水线。
- [ ] 确定性业务逻辑未强行改写成 Agent 任务。
- [ ] 页面通过核心公开入口发起任务并获取状态。
- [ ] 会话、运行、事件和产出物没有第二套状态存储。
- [ ] 模型结果经过业务校验后才写入业务数据。
- [ ] 用户、工作区、专家和业务对象权限均未被绕过。

## 十四、存量实现迁移规则

迁移目标是消除平行体系，不是把同一套复杂结构机械搬到另一个目录。

| 存量内容 | 目标处理 |
|---|---|
| 域 `SKILL.md` / 技能目录 | 页面不再依赖。确有通用价值的知识或流程评审后并入现有专家；仅服务单个页面的任务说明保留为业务任务模板。 |
| 域 Agent / 域专家团队 | 删除独立执行身份，改用核心 Agent 或已有专家；不得仅改名后继续独立运行。 |
| 域插件、子域插件映射 | 退出业务域设计。需要的专业能力由核心专家体系统一管理，页面只保存 `expert_id` 选择。 |
| 域专属工具 | 确定性读写改为业务 API / Store；通用文件、检索等能力复用核心工具；确属专家能力的内容评审后归现有专家。 |
| 独立 LLM / 多 Agent 流水线 | 改为向核心提交标准任务，由核心 Agent 或现有专家执行；业务域保留输入校验、任务组装和结果校验。 |
| 域独立聊天接口与消息存储 | 改用核心会话、消息和事件；业务表只保留业务对象与核心会话关联。 |
| 域独立模型配置 | 删除，使用核心模型路由和凭据。 |
| `DomainBundle` / `domains.yaml` | 保留为功能模块装配和构建裁剪机制，不再解释为能力插件体系。 |

迁移期间允许暂时保留旧实现以维持功能，但新增页面不得继续依赖旧模式；每次迁移都应以减少域内执行身份、运行状态和模型调用点为目标。

## 十五、规范结论

业务域不是“领域智能体平台”，而是“使用系统智能能力的业务功能层”。

- **页面可以懂业务，但不扮演专家。**
- **业务服务可以组织任务，但不执行第二套 Agent。**
- **功能可以指定现有专家，但不拥有或复制专家。**
- **核心能力必须可直接调用，且调用后仍受核心统一治理。**
